# Environment

`scripts/e2e-env.sh` (run it as `bash "${CLAUDE_PLUGIN_ROOT}/scripts/e2e-env.sh" <command> --worktree <worktree>`: your shell starts in the repository, where the script does not exist) starts the environment the config describes (`environment.*`). With `type` `none` (the default) there is nothing to start: tests run on the host and `up` only records that. With `type` `compose` it builds an isolated compose project named `df-<key>`, runs each `environment.setup` command inside `environment.service`, and polls `environment.pingUrl`.

| Command                                                           | What it guarantees                                                                                                                                                                                              |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `up --key KEY [--ports canonical\|direct\|none] [--device]`       | Environment started and `verify` passed. Exit 75 means a cap or the ports lock refused it: stop, a later pass retries.                                                                                          |
| `verify`                                                          | Compose config renders, every service is running or healthy, `environment.processCheck` (when set) exits 0 inside the service, and `environment.pingUrl` (when set) answers from inside it. Prints what failed. |
| `down`                                                            | `down -v` and forgets the environment.                                                                                                                                                                          |
| `sweep`                                                           | Removes `df-*` projects that no live owner file claims, unless their labelled owner is alive or their worktree changed in the last 3 hours.                                                                     |
| `node "${CLAUDE_PLUGIN_ROOT}/scripts/cleanup.mjs" --worktree DIR` | After every run: `down`, stops the dev server and the simulator this run booted, closes Playwright and Maestro sessions, frees the ports lock; prints what it did and what it left.                             |

Facts you rely on:

-   A remote environment (`e2e-env.sh up --worktree <worktree> --key <KEY> --remote <env> [--account <name>] [--device]`) starts nothing: it checks that the deployed address answers and records the account's variable NAMES in `.dev-factory/env.json`. `verify` pings it again and `down` only forgets the record. Sign in with `qa-login.sh` (mobile) or from the case through `process.env` (web), never by naming the variables in a command.
-   A finished run leaves nothing running. `cleanup.mjs` stops only what the run started unless the owner set `DF_TAKEOVER=1` in the environment (it is not a repository setting, and an agent cannot set it): then it also stops the processes and containers holding the ports the run needs (`cleanup.ports` adds more) and the leftover browser and Maestro sessions. It never touches the shell, Claude, the terminal or system processes, and an agent cannot switch the toggle on for itself.

-   `.dev-factory/env.json` holds `project`, `composeFile`, `mode`. Every container command is `docker compose -f <composeFile> -f .dev-factory/compose.override.yml -p <project> exec -T [-u <environment.user>] <environment.service> <cmd>`.
-   Isolated mode (`--ports none`) publishes no host ports and has no web-QA path: the Playwright browser runs on the host. Use `--ports canonical` (or `--ports direct`) for any ticket that needs a browser walk; `webBaseUrl` in `env.json` is the address to open.
-   Canonical-ports mode (`--ports canonical`, implied by `--device` without `--ports direct`) keeps the published ports and is machine-wide exclusive, across every repository. The pass picks the mode with `scripts/ports-mode.mjs`, which chooses `direct` wherever the engine allows, so tasks never wait on each other.
-   Direct-ports mode (`--ports direct`) publishes no ports and takes no lock, so several can be up at once. The host reaches the stack at its own address: `environment.webBaseUrl` with its host replaced by `environment.directHost` (`<service>.<project>.orb.local` by default, the name OrbStack gives a container; set `environment.directHost` for an engine that names them differently), and `webBaseUrl` in `env.json` is that address. It needs `environment.webBaseUrl`. `up` probes that address itself from this machine (not `environment.pingUrl`, which stays the check inside the service) and counts any HTTP answer below 500 as reachable; with no connection, or only a 5xx, within the ready timeout it exits 1, and that is an environment failure, with no fallback to canonical ports. It is refused with `--device` for now. A stack that is already up is reused when its mode is the same or stronger, in the order isolated, direct, canonical, device.
-   Run `verify` again before QA starts and after any service restart. A failing verify is never a reason to skip QA; it is a reason to block.

## Mobile (device lane)

Only when `mobile.appDir` is set. `up --device` starts the backend (canonical ports under the machine-wide lock, or with `--ports direct` its own address and no lock), then `scripts/mobile-env.sh up` prepares the host side for this run alone: it claims a simulator or emulator no other live run holds (the one named in the mobile profile of `qa/profiles.yaml` or `mobile.androidAvd`, booted ones first; when every one is held, a new simulator `<name> df<n>` or a further read-only emulator instance), runs `mobile.prepare`, `mobile.install` and `mobile.pods` when the app's dependencies are missing, starts the dev server with `mobile.start` from this worktree on a Metro port of its own (the first free one from `mobile.metroPort` up: 8081, 8082, ...; `DF_METRO_PORT` pins one, exit 75 if something else holds it), reverses an Android emulator to that port and, on a direct stack, each `mobile.androidReversePorts` port to a host proxy of its own task's container, runs `mobile.deviceSetup` (`mobile.androidDeviceSetup`) when the app is not on the device (installs a prebuilt client such as Expo Go), runs `mobile.build` only when a file matching `mobile.nativeInputs` changed since the last build on that device or the app is missing, warms the JS bundle, and runs `mobile.open` (`mobile.androidOpen`) every time to open the app on its Metro. The udid or serial, the device's own name, the Metro port and the reversed ports are recorded under `device` in `.dev-factory/env.json`; pass that device to every Maestro MCP call and name `device.name` in the evidence. `down` stops this worktree's dev server and proxies and gives back its claims; `scripts/cleanup.mjs` also shuts the simulator down again when this run booted it.
