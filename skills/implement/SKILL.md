# Implement

1. Read the ticket, its acceptance criteria, and, when present, `docs/plans/<KEY>/research.md` and the debugger's records in `.dev-factory/debug/*.json` (root cause, evidence, fix plan and validation plan of a bug ticket; start from them). Also read `CLAUDE.md`, any editor or agent rule files the repository keeps (for example `.cursor/rules/*.mdc` whose paths match the files you expect to touch), and the `AGENTS.md` files from each touched directory up to the root (their `## Learned rules` sections are standing rules). The prompt may list a few recent learnings that match this ticket's paths; treat them as hints, not requirements.
2. Find the seam: the smallest place where each acceptance criterion can be observed. Write the failing test first, run it (in the container when `.dev-factory/env.json` has a `composeFile`, otherwise on the host) and confirm it fails for the expected reason.
3. Make the smallest change that turns it green. Do not refactor beside it and do not add behaviour the ticket did not ask for.
4. Run the affected suites where the environment says: with a `composeFile` in `.dev-factory/env.json`, inside the container (`docker compose -f <composeFile> -p <project> exec -T [-u <user>] <service> ...`, values from `environment.*` in the config and `.dev-factory/env.json`), never on the host; with `mode` `none`, on the host with the repository's own test command.
5. Fix budget: three attempts per failing test. A fourth is not allowed. After the third failed attempt write `.dev-factory/blocked.json` with `{"reason": "<test, attempts, last error>", "decision": "what a person must decide"}`. For a bug ticket, write `.dev-factory/needs_debug.json` with `{"test": "...", "attempts": 3, "lastError": "..."}` instead and stop: the scheduler hands the stuck state to a fresh debugger and calls you again with its new hypothesis.
6. Commit after each green step with a message ending in the ticket key in square brackets. Commits are made as the person whose git identity this machine has: no `Co-Authored-By` line, no `--author`, no "generated with" text (`git.agentAttribution`, default false; the guard refuses them and `qa.mjs verify` checks every commit of the branch).
7. Never edit the plugin's own files, `.factory/tasks/` (the task tracker), `.claude/`, `.github/`, or another task's QA cases; your own cases live in `.factory/qa/cases/<KEY>/`. A hook refuses it.
8. Method skills: follow `superpowers:test-driven-development` for step 2, `superpowers:systematic-debugging` for the fix loop and `superpowers:verification-before-completion` before you claim anything is done. Look up library and framework behaviour with the `context7` tools when that MCP server is enabled (otherwise the repository docs and `WebFetch`) before coding against it, and record the source in the PR body.
9. UI work (a new or reshaped screen or component): if the `21st` MCP server is enabled, search it for a matching component first; then adapt the result to the repository's own design system and brand rules (look for them in `CLAUDE.md`, `AGENTS.md` and the rule files above). Never paste an unadapted result. If `frontend-design` is enabled, use it for layout and typography choices. For a hard design or architecture decision, use `sequential-thinking` when enabled, and write the decision and reason in the PR body.
