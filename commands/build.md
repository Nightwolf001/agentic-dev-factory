---
description: Build one Jira ticket interactively with the factory-builder agent (usage /dev-factory:build OAPP-1234 [--base <branch>])
argument-hint: '<JIRA-KEY> [--base <branch>]'
---

Build ticket $ARGUMENTS with the dev-factory flow, in this session, visibly.

1. Read the issue through the Atlassian MCP (cloud id and statuses from `dev-factory/config.json`): summary, description, acceptance criteria, type, links.
2. Pick the base branch: `--base` in the arguments, else a `Base branch:` line in the description (`node dev-factory/bin/qa.mjs ticket base --file <description file>`), else `git.baseBranch` (develop). Pick the branch `<type>/<KEY>-<slug>` (type from the issue type, slug from the summary) and create the worktree with `node dev-factory/scripts/worktree.mjs add --branch <branch> --path ../.worktrees/<KEY> [--base <name>]`; it branches off `origin/<base>` and keeps `.dev-factory/` out of git. Exit 2 or 3 means the base is unknown, not on origin, or behind your local copy: tell the person to push it and stop. Do not `cd` into the worktree: run every command from this session's directory and pass `--worktree <absolute worktree path>` to `qa.mjs` and `e2e-env.sh`. A worktree cut from a base that lacks the plugin has no `dev-factory/` folder to run them from.
3. Write `.dev-factory/run.json` there: `{"key","branch","base":"<name>","startedAt","mode":"interactive"}`, and point the hooks at it with `node dev-factory/scripts/run-context.mjs set --worktree <absolute worktree path>` (the session was started elsewhere, so `cwd` does not reveal the worktree).
   3a. Claim the ticket in Jira the way the scheduled pass does, so the board shows it moving: fetch its transitions and move it from its current status (Ready for Dev or To Do) to `jira.statuses.inProgress`; skip this when it is already In Progress. Add the comment `[dev-factory] phase: claim started (interactive) base=<name>`. If Jira refuses the transition, say so and carry on.
4. Start the environment: `bash dev-factory/scripts/e2e-env.sh up --worktree <worktree> --key <KEY> --ports canonical` (use `--device` instead for a mobile ticket). Exit 75 means retry later.
   4a. Triage: for a bug or a ticket linking a Sentry issue or Axiom query, set `role` `debugger` and `debugBefore` in run.json, dispatch `factory-debugger` with trigger `triage` and the selected environment (`env:<name>` label, else the Sentry issue's tag, else `staging`), wait for a recorded round in `.dev-factory/debug/` or `blocked.json`, then set `role` back to `builder`. If the builder later writes `needs_debug.json`, dispatch the debugger with trigger `unstick` and re-dispatch the builder.
   4b. Prepare: for a ticket labelled `needs-research` or with a `Research:` block, set `role` `researcher` in run.json, dispatch the `factory-researcher` agent, wait for `docs/plans/<KEY>/research.md`, commit it, and set `role` back. Skip otherwise.
5. Write `role` `builder`, `until` `build` into run.json and dispatch the `factory-builder` agent with the key, worktree path, branch and the ticket text. Wait for `.dev-factory/build.done` or `blocked.json`.
   5b. Review in two steps exactly as `commands/tick.md` section 4 step 6 describes (spec reviewer, then standards reviewer, fix rounds up to `caps.maxFixRounds`), dispatching `factory-reviewer` with the matching `role` and `axis` in run.json. Show the findings to the person after each step.
   5c. Write `until` `ship`, dispatch the builder for the ship phase only, and wait for `.dev-factory/ship.done` or `blocked.json`.
6. Read the result from files and GitHub, not its narrative: `.dev-factory/ship.done` or `.dev-factory/blocked.json`, `gh pr view <branch> --json url,state`.
7. Move the ticket on, as `commands/tick.md` section 5 does: after `ship.done` and a PR that passes `qa.mjs verify`, transition it to `jira.statuses.peerReview` and comment `[dev-factory] phase: ship done pr=<url> qa=<verdict>`. After `blocked.json`, follow `commands/tick.md` section 6 (label `factory-blocked`, comment the reason and the decision needed, move it back to To Do). Write each comment to a temp file and run `node dev-factory/bin/qa.mjs scrub --file <file>` before posting it. Merge and approval stay with people: a later scheduled pass moves a merged or approved ticket to Ready for QA.
8. Report to the person: PR URL, QA verdict, blockers, and where the ticket now sits in Jira.
9. Tear down: `bash dev-factory/scripts/e2e-env.sh down --worktree <worktree>`.
