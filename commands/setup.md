---
description: Guided first-time setup - choose a task source, MCP servers, plugins, secrets and environment, each for all projects or this project, saved through the settings page (usage /dev-factory:setup)
---

You set the factory up for this repository with a person. Nothing here needs an account the person does not already use, and every question has a working answer that needs no tracker and no MCP server. Every answer is saved with `node "${CLAUDE_PLUGIN_ROOT}/scripts/settings.mjs" set <id> <value> [--user|--project]`, which writes the right layer, refuses what is not allowed (a required server cannot be off) and makes Claude match. Never write a settings file, a `.mcp.json` entry or a secret by hand: the settings page is the one writer, and it is idempotent (setting a value that is already set exits 0 and says so).

Where an answer is saved: **all projects** is the person's own settings file (`--user`, for choices that are the same on every repository: models, a server such as `playwright`, a plugin); **this project** is `.devfactory/config.json` in this repository (`--project`, for what is true only here: the task source, the project keys, the environment, a telemetry server). The folder ignores itself, so nothing is committed.

1. **Look first**, then tell the person what you found in two lines:
    - `node "${CLAUDE_PLUGIN_ROOT}/scripts/config.mjs" validate` (it prints a `note:` for a legacy file in use), `node "${CLAUDE_PLUGIN_ROOT}/scripts/settings.mjs" list`, `gh repo view --json nameWithOwner 2>/dev/null`, `git remote -v`, the repository's default branch (`node "${CLAUDE_PLUGIN_ROOT}/scripts/worktree.mjs" default-branch`), its test command and CI, and `claude mcp list` (a server the person already has, at user scope or as a claude.ai connector, is used as it is and is not added twice).
    - Legacy files: `ls dev-factory.config.json dev-factory.qa.yaml .factory/qa/cases .mcp.json 2>/dev/null`. The old `dev-factory.config.json`, `dev-factory.qa.yaml` and `.factory/qa/cases/` are legacy locations, still read for one release. When any exist, show the plan with `node "${CLAUDE_PLUGIN_ROOT}/scripts/project-dir.mjs" migrate` and, on a yes, run it with `--apply`; it moves them into `.devfactory/` and prints the `git rm --cached` lines for the tracked ones, which the person runs themselves. A legacy `.mcp.json` is read, never written: offer `node "${CLAUDE_PLUGIN_ROOT}/scripts/mcp.mjs" migrate` (add `--apply`) to move the factory's own entries into the settings.
    - Read the build files and propose answers from them rather than asking blind: a `docker-compose.yml` or `.devcontainer/` gives the compose file and the service (the one with `build:` and the repository mounted); read that service's `command` and the startup scripts it runs, because when the container already installs and starts the app (as a pm2 start in its command does) `environment.setup` is empty; the published `ports` tell you which host ports a UI walk needs free (they must be `--ports canonical`, one task at a time); a health or ping URL comes from the app's own health route (for example `/_health` on Strapi) or its web port, checked from inside the container; `.husky/` or `lint-staged` means the commit hook may need the container's tools, so offer `environment.preCommit`; `.nvmrc` and `package.json` scripts give the test commands.
2. **Walk the rows that matter for a first run**, one question at a time, each with your recommendation, and save each answer as you get it:
    - **Where will it run?** On this machine only (launchd on a Mac), in Claude Code on the web, on a GitHub Actions schedule, or a Claude Code routine. For anything but this machine, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/cloud.mjs" init` (add `--github-actions` or `--routine`) after the settings are saved; it commits the marketplace and enabled plugins to `.claude/settings.json` so cloud sessions install the plugin themselves, and tells the person to set `DF_PROJECT_CONFIG` and `DF_PROJECT_QA` for the session (the project folder is never committed). Say what changes there: no Docker or simulator unless the runner has them, a `github`, `notion` or `jira` task source (a `local` source only sees committed task files), and `git.worktreeRoot` if the checkout's parent folder is read-only.
    - **Where do tasks live?** `tasks.source`, saved with `--project`: `local` (markdown files in the repository, no account), `github` (Issues via `gh`, no MCP server, recommended when the repository is on GitHub), `notion` (a database; needs a Notion integration token and the Notion MCP server), `jira` (needs a Jira API token). Then the keys that source needs: `sources.github.repo`, `sources.notion.databaseId`, or the `site`, `cloudId` and `projects` keys under `sources.jira`; for Jira also the sprint rule (`requireSprint` there) and `improvement.project`, if the person wants improvement tasks filed in another project. Details: `skills/task-source/`.
    - **What do they need to build a task?** The test command, whether there is a web UI to walk (Playwright), a mobile app (`mobile.appDir`, which makes Maestro required), a docker compose environment (`environment.type` `compose`, with its service, setup commands and ping URL) or neither (`none`, tests run on the host).
    - **Which MCP servers?** Take them from `node "${CLAUDE_PLUGIN_ROOT}/scripts/mcp.mjs" recommend`. Ask each one you would suggest, and every one the person raises, as **all projects / this project / off**, and recommend the scope in that server's `defaultScope` in `mcp/catalog.json` (`user` or `project`). Save it with `settings.mjs" set <id> user --user`, `settings.mjs" set <id> project --project` or `settings.mjs" set <id> off`. `playwright` is required (its scope can change, it cannot be off), and so is `maestro` once `mobile.appDir` is set. When `tasks.source` is `jira`, ask which Jira server: `jira` (this plugin's API-token server, recommended when `JIRA_EMAIL` and `JIRA_API_TOKEN` can be set, since it survives unattended passes) or `atlassian` (the Atlassian OAuth server, one `/mcp` login, which does not survive unattended passes). Never offer both, and do not ask this for any other task source.
    - **Which plugins?** `node "${CLAUDE_PLUGIN_ROOT}/scripts/plugins.mjs" list` shows them. `superpowers` is required. Ask each optional one the same way (all projects / this project / off), recommend its `defaultScope`, and save with `settings.mjs" set <id> user --user` or `--project` or `off`.
    - **Telemetry?** Sentry or Axiom for bug triage and post-merge validation, saved as `project` (their `defaultScope`). Skippable; bugs are then triaged from the task and a reproduction.
    - **Branches and PRs:** the base branch (default: the repository's), the branch types, size and area labels. Skippable; the defaults work.
    - **Secrets.** `node "${CLAUDE_PLUGIN_ROOT}/scripts/mcp.mjs" secrets` lists the variables the chosen servers and task source read, set or empty (never a value). For each that is empty and needed, a value goes to `~/.dev-factory/.env.local` only, through standard input: `node "${CLAUDE_PLUGIN_ROOT}/scripts/settings.mjs" set secret:<NAME>` reads it from a pipe and refuses a value on the command line. The value must never pass through this conversation: never echo, print or write a secret, and never ask the person to paste one to you. Tell them to run it themselves with `!` so the value comes from their clipboard or their own shell: `! pbpaste | node "${CLAUDE_PLUGIN_ROOT}/scripts/settings.mjs" set secret:JIRA_API_TOKEN` (or `printf %s "$VALUE" | ...` when it is in a shell variable, or `dev-factory settings` in their own terminal, which masks what they type). `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`) is needed only for unattended passes. A token Claude itself expands in a server's config (`GITHUB_PERSONAL_ACCESS_TOKEN`, `CONTEXT7_API_KEY`) must also be exported in the shell that starts `claude`; say so.
3. **Make it real.** If any answer changed a server or plugin, `settings.mjs set` has already synced; run `node "${CLAUDE_PLUGIN_ROOT}/scripts/mcp.mjs" sync` and `node "${CLAUDE_PLUGIN_ROOT}/scripts/plugins.mjs" sync` once more anyway (they only do what is missing), prepare the source with `node "${CLAUDE_PLUGIN_ROOT}/scripts/tasks.mjs" init` (creates the labels or the folder; for notion and jira, say what to create by hand), then run `node "${CLAUDE_PLUGIN_ROOT}/scripts/config.mjs" validate` and `bash "${CLAUDE_PLUGIN_ROOT}/scripts/doctor.sh"`, and report each FAIL and warn with its fix. Do not edit anything the doctor flags without asking. A server that uses OAuth needs one login no script can do: the person starts `claude` and runs `/mcp`.
4. **Once per machine**, in the person's terminal: `claude plugin install dev-factory@dev-factory --scope user` installs the plugin for every project (skip it when `claude plugin list` already shows it at user scope). Then make `dev-factory` available in their own terminal: show the plan with `bash "${CLAUDE_PLUGIN_ROOT}/scripts/install.sh"`, and on a yes run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/install.sh" --apply` (it writes `~/.dev-factory/bin/dev-factory`, the machine's env file and, on a Mac, the launchd jobs only with `--load`). Tell them to add `~/.dev-factory/bin` to PATH.
5. **Finish** with the next step: `/dev-factory:plan "<idea>"` to create tasks, `/dev-factory:quick "<change>"` for a small change with no task, or `bash "${CLAUDE_PLUGIN_ROOT}/scripts/install.sh" --apply --load` to schedule unattended passes on this Mac. Tell them every choice made here can be changed later, with its value and where it comes from, on the settings page: `dev-factory settings` (or `dev-factory settings list`, which prints it).
